# 2. Tool output formatter failures in a production system

The production system we audited is a deployed research assistant for a digitized historical archive of 17,807 documents. Its agents query the archive through tools. A tool output formatter is the code that turns a tool implementation's internal result into the text a model reads. Below, we call this code the formatter. Our audit of the formatter layer found four defect families.

The first is a scope defect, where the tool claims to have more coverage than it really does. For example, the `find_in_document` tool could report a false absence. The tool inspected at most the first 1,000,000 characters of each searched field. Although found matches carried a notice when this limit applied, a miss said "Searched the FULL text" and omitted the limit. The archive contained 14 documents with at least one transcript longer than the cap. In 7 of the 14, at least one term first appeared beyond the limit and nowhere before it in any field searched. A query for such a term returned no hit even though the unsearched text contained it. For one reproduced query, the term began at character position 1,000,072 in a 1,031,201-character transcript.

The second defect type is completeness. The `keyword_search` tool had a configurable limit for results. The tool was attached to the RAG agent with a sane 10 result limit for efficiency. However, the formatter downstream had no access to the total number of results in the database, only the results which actually got fetched. It began the output by counting what had been fetched: "Found 10 document(s)". In the production incident behind this study, 191 documents actually matched the search, and nothing in the output said so. Every statement in the output was technically true, but the truncated list read as the complete result set, and treating it that way contributed to an agent giving incorrect information to a user. Maintainers fixed that formatter in ordinary development. A similar defect was found in the `date_range_search` tool when starting this research paper: it fetched at most 20 results, its formatter opened with "Found 20 document(s)", and for the year 1920 the archive actually held 4,772 matches; 90 distinct years had more matches than one fetch could return. Section 3 studies that instance.

The third defect type is uncertainty, where the formatter is unclear about the degree of certainty of its results. For example, the `find_in_document` tool maps the character position of a match proportionally onto the document's scans to estimate a page number. In an early draft caught in code review before merge, the formatter did not label it as an estimate, and an agent would have presented a guess as an exact page number, hurting user trust. We recreated it for testing and examine it in Section 3.

The last defect type is provenance, where the formatter does not explain where a piece of information came from. For example, our system had two types of numeric IDs, one for documents and one for page scans. These were simple integers and could easily be mistaken for one another. All but two of the 17,807 document IDs were also valid scan IDs for some unrelated item. If an agent trying to fetch a scan passed a document ID by mistake, the API would return a 200 OK along with a completely unrelated scan. Tool output presented these IDs without saying which numbering system each belonged to, creating ambiguity. That ambiguity caused a production incident: an agent cited a document ID as a scan, producing a valid-looking reference to the wrong item. Maintainers fixed that path before this study.

Of the four families, examples of both scope and completeness defects above were live when this study began and were fixed during the research phase of this paper.
